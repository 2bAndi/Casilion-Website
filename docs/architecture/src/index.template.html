Architecture concept

Cassilion Web Platform

Shop, licensing, customer MCP and guarded AI first-level support for the Cassilion database

  • Version 0.3 — concept, with a first runnable skeleton
  • 20 November 2026
  • Status: skeleton runs locally; decisions taken and open in section 12

This document proposes how to build the website that sells and supports Cassilion: one Django application for the public site, customer area, shop, licenses and support desk, and a separate, isolated AI enclave that does the first-level analysis of support tickets. It is a basis for decisions, not a specification. Plan names, quotas and response targets are placeholders.

New in version 0.3Three decisions taken after the first run of the skeleton. The stack stays Python and Django, as in the two Tango projects, although other projects of the same owner run on Node.js. The whole site takes the look of the landing page (dark ground, amber signal colour, cool blue for everything that is not Cassilion); the landing page itself has been ported into the application and is its home page, with the plans fed from the shop's database. For licenses, a signing service is the target and a person issues and uploads them at the start; the details are deferred. Decisions D4, D16 and D17 in section 12.

New in version 0.2The repository now holds a skeleton that runs the whole path on one machine: registration, Community license, sandbox purchase, download, ticket, AI analysis behind the guards, review in the backoffice, and both MCP servers. The table below lists what changed against version 0.1 and why. 1The proposal in brief

The platform has seven jobs: present and document Cassilion; register customers worldwide; issue licenses, free without support and paid with yearly support plans; deliver downloads; run a support desk whose first line is an AI that tells usage errors from probable product bugs; offer all of this to customers' AI agents over MCP; and keep the operators in control of everything that leaves the house.

2Scope, assumptions and quality goals

In scope: public site and documentation delivery, registration and customer area, plans and checkout, license issuing, downloads, support tickets, AI first-level support with guardrails, customer and operator MCP, backoffice, deployment from a local machine to production.

Out of scope: the Cassilion database itself, brand and content, price strategy, the legal texts.

Assumptions

  1. Cassilion ships as closed-source binaries. The private source repository is the main asset to protect.
  2. There is no support or CRM staff. The engineers are the operators, one to three people, with no round-the-clock duty.
  3. A few hundred active customers, highly technical, most of them working with an AI assistant of their own. Tens of tickets a week at most.
  4. Customers are private persons and companies anywhere in the world. The site starts in English and German.
  5. Paid plans are yearly subscriptions for support. Using the software is free under the Community license.
  6. Development is local first on Windows 11; production runs on a server in the EU.
  7. Support has no chat and no phone. The channels are the customer's AI agent over MCP and the customer area on the website, both on the same case store.

5.2Accounts and international customer data

  • A user is a login: e-mail, passkey or password, MFA. An account is the customer: a person or a company. Users belong to accounts through memberships with a role (owner, billing, technical).
  • A private customer is an account of kind individual with one member. Licenses, subscriptions and tickets therefore always belong to an account, never to a login, and a company can add or remove staff without losing anything.
  • Addresses start with the country (ISO 3166-1) and adapt to it; postal code and state are optional where a country has none. What the customer entered is stored as entered.
  • Company data: legal name, VAT ID with validation for EU companies, a billing e-mail separate from the login e-mail.
  • Consents are versioned: terms, license agreement, privacy notice. Marketing consent is separate and off by default.
  • Customers can export and delete their data from the customer area. Invoices and audit records stay as long as tax law requires.

5.3Data model

5.4From registration to license

Superseded in partThe second and third points below were written before the product's functionality summary was available, and they are wrong about the product. A Cassilion license binds a cluster, product and version, edition, capacity, term and feature entitlements. It carries an ES256 and an ML-DSA-65 signature, and a separate offline tool, zuri_license_issuer, creates, inspects, rotates and revokes it; remote signing is deferred on the product side. When a license expires, the cluster goes into a controlled read-only grace state and then a recovery-only state. Three consequences: the website cannot sign licenses; a customer has to name a cluster before a license can exist, so registration alone does not yield one; and the end of a support plan must not be tied to the end of a license by accident. The flow to design is request, issue, deliver: the customer area takes the request, the issuer runs offline, the result is stored and offered for download and over MCP. Figure 4 and appendix A.1 show the version 0.1 idea and are kept for reference only.

  • An entitlement says: account X has plan Y from one date to another. The platform reads it for every support action.
  • A license file is the entitlement in a form the database verifies offline: a small JSON document with an Ed25519 signature. The public keys ship inside the binary; a key ID allows rotation. Appendix A shows an example.
  • The file identifies customer and plan. It does not unlock the software, since the Community license already permits use. The recommendation for D4: the database never refuses to start because a paid plan lapsed. It reports the plan and writes the license ID into its diagnostics bundle, so a ticket can be matched to a customer and an exact build.
  • The signing key lives outside the repository and outside the web process. Every issued file is written to the audit log.
  • Webhook handling is idempotent: each provider event is stored once and applied once, so repeats and reordering do no harm.

5.6Downloads

  • CI publishes signed builds with checksums into object storage and registers them in the release catalogue.
  • A download needs a signed-in account that has accepted the current license agreement. The link is valid for minutes.
  • Each download is recorded with account and version. Support uses this, and it is the mailing list for security notices about a specific release.

6.2Authorization

In the skeletonFigure 6 is the target. The skeleton takes a shorter road to a working agent connection: in the customer area a customer creates a personal agent token, shown once, stored as a hash, revocable, valid for one account; the agent sends it in the Authorization header. A setting makes two-factor authentication a condition for creating one (on outside development). The endpoints already behave like an OAuth resource server (401 with a pointer to the protected-resource metadata, tokens bound to one endpoint), so OAuth replaces the token source and nothing else. Until then, only MCP clients that can send a custom header can connect; clients that insist on an OAuth sign-in cannot.

The current MCP revision is 2026-07-28. Two properties shape the design. The protocol core is stateless: there is no session handshake, each request carries what the server needs, and the MCP endpoint is an ordinary HTTP route behind the proxy. And authorization is OAuth 2.1 with fixed roles: our MCP server is a resource server, our login is the authorization server.

  • The MCP server publishes protected-resource metadata. A request without a token gets a 401 that points to it and names the scope needed.
  • Tokens travel in the Authorization header on every request. The server checks that a token was issued for this MCP server and accepts no other. It never passes a token on.
  • Clients identify themselves with a Client ID Metadata Document. Dynamic client registration is deprecated in the specification; we add it only if a client we care about still needs it.
  • PKCE, exact redirect URIs, short-lived access tokens. A call that needs more than the token allows gets a 403 that names the missing scope.
  • Implementation: the official Python SDK 2.x as an ASGI app beside Django. It speaks the new revision and still serves clients on the older ones. The login can come from django-allauth's OpenID Connect provider or from django-oauth-toolkit; a short spike against real clients in phase 5 decides.

6.3Rules that are specific to MCP

  1. One service layer. MCP tools and web views call the same functions, so entitlement checks, quotas and guardrails cannot be bypassed through the other door.
  2. Text that arrives through MCP is treated exactly like form input and passes G1 and G2.
  3. AI-written text leaves through MCP only after G4 and G5. Tool descriptions are fixed text and are reviewed like code.
  4. No payment through MCP. get_checkout_link returns a URL; paying happens in the browser.
  5. Scopes follow the plan. A Community token cannot hold support:write; the tool answers with the upgrade link.
  6. Rate limits per token and account. Results are paged and capped in size.

7AI first-level support

7.1Principles

  1. Assume each guard can fail. Arrange things so that one failure is harmless.
  2. Least capability. The AI reads a fixed corpus and writes a structured result. It cannot send, browse, look up customers or change anything.
  3. Separation of knowledge. What is said to customers is generated from public material only.
  4. A person decides until the numbers say otherwise.
  5. Everything is recorded: input, retrieved documents, model and prompt version, guard verdicts, who released the reply.

The one idea to keepOutput filters are probabilistic. The wall between Analyst and Responder is not: the model that writes to the customer has never had the private source in its context. G4 exists to catch a mistake in building that wall, not to be the wall.

7.6Operator oversight

  • Review queue: draft, finding with pointers and guard report side by side; approve, edit or reject. Edits are kept as evaluation examples. There is no assignment and no ticket ownership: whoever looks, decides.
  • Bug alert: e-mail and push with ticket ID, plan, version, class, confidence, summary and pointers, plus a draft issue for the tracker.
  • Sent log: every outgoing reply, including automatic ones, with its guard report; a daily digest.
  • Switches: a global kill switch for automatic sending, switches per class and per plan, and a sampling rate for after-the-fact review.
  • Measures: share of tickets resolved without a person, how often reviewers edit, guard blocks, confirmed bugs among candidates, cost per ticket.

7.7Knowledge and retrieval

  • Public corpus: documentation, release notes, known-issues list, FAQ. Built from the same source as the documentation site; every passage has a stable ID and URL.
  • Internal corpus: the source tree per release tag and internal design notes; later also closed tickets with approved answers.
  • Version pinning: the ticket carries the product version from the form or the diagnostics bundle, and the Analyst reads the matching tag. An answer about the wrong version is a wrong answer.
  • Analyst tools, all read-only on a snapshot: search documentation, search code (exact and semantic), read a file range, list symbols, look up known issues for a version.
  • The index is built inside the enclave from its own Git fetch. Nothing of it exists on the application server.

Recommendation for D2: start with A in shadow mode, collect 50 to 100 real tickets from beta users as an evaluation set, and decide with results. The model sits behind an OpenAI-compatible gateway, so changing it is configuration. Because the Responder handles public material only, it could later use a different, stronger model than the Analyst without touching the question of where the source code may go.

In the skeletonThe default backend is a stand-in without any model (LLM_BACKEND=stub): keyword rules for crashes and security, a known-issue match, and a text search over the public documentation whose score decides between an answer, a request for information and a documentation gap. It is deterministic, which is what the tests need, and it is not smart. It cannot judge whether a question is out of scope, and it reads no code. With LLM_BACKEND=openai the same pipeline calls an OpenAI-compatible endpoint for both stages; if the endpoint fails, the rules take over and the finding is marked low confidence, so it lands in review. The model path is tested against a stand-in endpoint only, not yet against a real model.

7.9End to end

7.10Cost control

Each AI run counts its tokens. There is a ceiling per ticket and a budget per plan and month. When a budget is used up, tickets wait for a person or for the next period, depending on the plan. The operator tools costs and set_budget follow the pattern already used in the Tango-Kalender back office.

9Environments: local to production

  • Local: python manage.py dev starts the web application with both MCP endpoints and the AI worker as a second process, on SQLite, with mails on the console and a stand-in payment provider. No Docker is needed. The worker uses rules by default and an OpenAI-compatible endpoint, for example Ollama on the GPU workstation, when configured.
  • Production: decided: cassilion.com and cassilion.de point at the server that also runs Tango-Kalender, and the whole application runs there from the start, with search engines kept out (SITE_NOINDEX). The procedure is docs/server-setup.md: host nginx, a Compose stack on a local port, nightly backup. While the AI worker works by rules it runs in that stack; with a model or the product source it moves to its own machine. Version 0.1 recommended a separate server, because this application holds customer data and receives payment webhooks; on a shared machine the same separation has to come from its own containers, database, system user and backups. The product source and the model stay off that machine in every case. The AI node is our own GPU hardware or a dedicated server and needs only an outbound connection, so it can sit behind an ordinary router.
  • Host names: www for the site, mcp for the customer MCP, ops for backoffice and operator MCP with network restriction.
  • Configuration comes from environment variables. Secrets and the signing key are never in the repository.

Where the skeleton stands. It cuts through P0 to P5 once, thinly, instead of finishing one phase after the other: every step of the path exists and is covered by a test, and none is production-ready. What is real: data model, entitlement and quota logic, license signing, job API, guards, release gate, review and sent log, both MCP servers. What is a stand-in: the payment provider (sandbox), the model (rules), the documentation and known issues (invented examples), legal pages (empty), the MCP sign-in (agent tokens). What is missing: invoices and tax, renewals driven by a real provider, German texts, backups, rate limits, an evaluation set, deployment.

A.2 Job API, sketch

POST /internal/jobs/claim           200 { job_id, ticket }   or   204 nothing to do
                                    ticket = { text, attachments, product_version,
                                               plan, language }
POST /internal/jobs/{id}/heartbeat  extends the lease while the job runs
POST /internal/jobs/{id}/result     { finding, draft, guard_report, usage }
POST /internal/jobs/{id}/fail       { reason }   back to the queue, or to human review

The AI node authenticates with mutual TLS or a short-lived signed token, on a host name that accepts its address only. A job is leased, not handed over: if no result arrives in time, it is offered again or escalated to a person.
